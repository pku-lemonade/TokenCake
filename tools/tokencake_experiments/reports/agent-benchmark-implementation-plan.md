## 1. 目标与范围

在真实 agent 任务上，比较原生 vLLM 和 TokenCake 的任务质量、端到端性能及 KV 行为。
任务执行包含真实模型生成和真实工具操作，后继请求使用本次实际生成的历史。

| 项目 | 选定方案 |
| --- | --- |
| BFCL 数据 | 多轮 Base 和 Long Context 两类；已完成每类 2 题的功能试跑，完整 400 题评测取消 |
| BFCL Agent | 官方多轮 runner 和对应模型 handler |
| BFCL 评分 | 官方多轮检查器，保留状态和必要执行路径检查 |
| SWE 数据 | SWE-bench Verified 的 test 集 |
| SWE Agent | mini-swe-agent 官方文本动作模式 |
| SWE 试跑 | 固定 20 个任务，验证完整执行、环境和评分流程 |
| SWE 正式评测 | 原定全部 500 个任务，已按用户要求取消 |
| 部署位置 | 数据盘 `/root/autodl-tmp`，包含环境、代码、缓存、任务目录和结果 |
| SWE 执行后端 | 官方 `LocalEnvironment`，不依赖 Docker 服务 |
| SWE 评分后端 | 本地适配测试执行，复用官方测试集合、日志解析和判定规则 |

BFCL 的 V3 官方说明中，两类各有 200 个任务；实际代码版本、数据版本和条目清单在准备阶段核验并冻结。
20 个 SWE 任务只用于试跑，不标为 500 题的正式成绩；已下载的完整数据和环境准备记录保留。

这两套 agent 默认顺序调用模型，主要覆盖多任务排队、容量准入、前缀复用和工具窗口 KV 保存。
它们不能单独证明并行分支汇合优化，也不能将同一类 agent 的测试解释成跨类型预留借用的完整验证。
本轮不引入额外并行 agent、其他 benchmark、人工工具等待或固定轨迹回放来替代真实任务评测。

## 2. 本地执行与评分环境

### 2.1 环境准备

每个 SWE 任务检出数据集中指定的 `base_commit`，使用独立任务代码目录和对应版本的 Python、项目依赖。
Benchmark 客户端、任务依赖和 vLLM 服务环境分别管理，避免把历史项目依赖安装到 vLLM 环境中。
环境管理优先使用 `uv`；用户明确授权 uv 无法支持时使用服务器 `/root/miniconda3/bin/conda`。
每题解释器入口保持为数据盘任务目录的 `.venv/bin/python`。

2026-09-08 环境验证结果：候选 20 题全部已验证原始版本与参考修复的测试表现。
其中 Xarray 3677 和 Matplotlib 22865 含有 Conda 特有依赖，uv/PyPI 适配无法直接复现。
早期依赖解析保存了完整官方配方的精确包锁；实际安装改用用户指定的服务器 Miniconda。
使用独立前缀、复制安装和完整快照；安装后核对版本和 build，再验证原始版本与参考修复。
Conda 安装写共享包缓存时串行化，任务执行仍并行；具体证据见 [实施状态](agent-benchmark-platform-status.md)。
全量中的 Python 2.7/3.5 三题已接入同一 Miniconda 后端，使用任务解释器及冻结的 pip 安装依赖。
安装成功与参考测试验证分开记录；原始版本的 F2P/P2P 不符合预期时，不能仅凭参考补丁被判 resolved 宣称环境有效。
全量 Astropy 环境已继续验证：旧依赖由冻结的 Miniconda Python/pip/setuptools 构建 wheel，再由 uv 安装；旧式项目安装经 `uv run` 调用任务解释器中的冻结 pip。
精确子模块缓存、准备进程覆盖项、安装及评分记录见 [Astropy 环境验证](agent-benchmark-astropy-environment-validation.md)，模型配置及测量预算保持原清单设置。
后续补齐 111 道 Django 评分脚本的任务本地 locale 初始化，新增 6 题通过环境验证；试跑受影响四题的四组保存预测复核结果一致。
原始失败、下载中断、全量进度及新评分环境见 [Django 环境与评分复核](agent-benchmark-django-environment-validation.md)。

准备阶段需要核验历史 Python 版本、操作系统库、编译器和项目安装要求。
独立目录和虚拟环境可以分开任务文件与 Python 依赖，但不提供容器级隔离，也不能替代系统依赖准备。
每次对比都使用干净的任务状态，分别管理任务临时文件和缓存，防止并发任务或前次运行相互污染。

当前机器曾确认缺少 Docker 命令和宿主 Docker socket，用户命名空间创建也被拒绝。
本计划使用普通本地子进程执行，不把解决 Docker 或用户命名空间权限作为接入前提。
尚未验证全部 500 个任务都能在本机复现依赖；环境失败需要保留记录，不得通过静默换题或删题处理。

### 2.2 本地评分适配

SWE-bench 当前标准本地评分入口使用 Docker，切换 mini-swe-agent 的环境参数不会同时解决评分部署。
本轮需要为本地环境适配测试执行流程，并复用官方测试集合、日志解析器及 `FAIL_TO_PASS`、`PASS_TO_PASS` 判定逻辑。

评分在独立、干净的目录进行，与 agent 修改的工作目录分开。
在独立评分环境中核对原始版本与参考修复的测试表现，验证依赖、测试命令和结果解析的一致性。
参考修复和评分专用信息不得作为 agent 输入或调度元数据。
报告明确注明使用自定义的本地执行环境，不直接假定与官方容器环境的结果完全一致。

### 3.2 四个对比组

| 报告名称 | Agent 调度 | 工具窗口 KV 保存 | CPU KV |
| --- | --- | --- | --- |
| `base` | 关闭 | 关闭 | 无 |

| `offload` | 关闭 | 开启 | 100 GiB |

`offload` 仍然使用保存资格、生命周期等元数据，不解释为完全不使用 agent 信息的策略。
原生通用 CPU offload 的第五组不在当前选定矩阵中。

四组使用相同任务集合、提示构造规则、采样参数、执行预算和工具环境。
不同运行的实际生成结果可能不同，因此同时记录模型调用量、输入输出 token、任务质量和失败情况。
各次运行复位服务与任务状态，使用独立输出目录和评分标识，避免复用旧预测、评分结果或完整模型响应缓存。
原生前缀缓存和本轮被测的 KV 缓存能力按对应配置正常启用。

执行顺序更新为：先完成 `agent_offload`、`base` 的比较，再进行 `agent`、`offload`。
首轮使用每组 16 并发、固定任务顺序的闭环到达，两组在各自服务就绪后同步开始测量。
首对 GPU 分配固定为 GPU 0 `base`、GPU 1 `agent_offload`，每卡独立模型服务，TP/PP 均为 1。
两组共享 36 核 CPU 配额和 240 GiB cgroup 内存；cgroup 观测属于整台实验实例，不能重复相加或归因给单组。
测量预算按两组运行区间的并集计时，重叠时间只扣一次；模型加载、环境准备和离线评分单独记录。
同一组任务的各个配置使用相同并发设置，并记录实际到达序列。
SWE 的 20 题试跑最多支持 20 个不同任务同时执行；BFCL 的四个功能验证样例不能代表 16 并发压力测试。

## 4. 首轮执行预算

以下参数已用于首轮试跑；正式压测已取消，不在收尾时调整模型、步数或超时。

| 参数 | BFCL | SWE-bench |
| --- | --- | --- |
| 采样 | `temperature=0`、`top_p=1`、`n=1` | 相同 |
| 单次输出上限 | 最多 4096 token，按剩余上下文空间收紧 | 相同 |
| 停止条件 | 官方停止规则和正常 EOS | 官方提交动作和正常 EOS |
| 步数限制 | 官方 `MAXIMUM_STEP_LIMIT=20` 及逐个用户轮次的原有计数逻辑 | 每个任务最多 250 个 agent 步骤 |
| 单次模型请求超时 | 600 秒 | 600 秒 |
| 工具超时 | 保留官方执行器规则 | 每条 shell 命令 60 秒 |
| 整个任务超时 | 30 分钟 | 60 分钟 |
| 上下文耗尽 | 记录明确失败 | 记录明确失败 |

BFCL 的步骤限制不改写成整个多轮任务总共只能调用模型 20 次。
单次输出预算按实际请求的 token 长度计算，保证输入与声明输出预算适配服务端上下文限制。
SWE 保留官方工具输出处理规则，不额外压缩或减半历史对话。
本地推理使用步数和时间约束，关闭不适用于本地模型的美元费用限额。
所有超时、停止和重试规则在四个对比组中一致。

### 4.1 重试与异常

- 关闭 SDK 和模型封装中的隐式重试，避免无法追踪的实际模型请求。
- 连接建立失败、明确拒绝请求的 429/503，最多重试两次，间隔为 1 秒、2 秒。
- 请求已经发出后的读取超时不自动重试，记录服务失败并处理请求及任务清理。
- 工具执行错误由 agent 按官方流程处理；适配层不自动重放 shell 命令。
- 每次模型请求重试使用新生命周期 ID；事件重试保留原 ID 和完全相同的事件内容。
- 重试、退避及事件交互开销计入任务耗时，不通过截断输入或缩短任务换取成功完成。

## 5. TokenCake 客户端适配

### 5.1 接入位置

| 部分 | 实现内容 |
| --- | --- |
| BFCL 模型 handler | 在现有请求构造处注入元数据，保留对应 handler 的格式化、API 类型和响应解析 |
| BFCL 工具执行 | 在真实函数执行阶段接入生命周期事件，保持官方执行顺序和状态检查语义 |
| mini-swe-agent 模型层 | 使用官方文本动作模式连接本地模型，加入请求身份、元数据和观测记录 |
| mini-swe-agent 环境层 | 在真实本地 shell 执行前后接入事件，保持官方动作解析、观察消息和提交流程 |
| 实验驱动 | 管理任务到达、配置组合、状态隔离、记录和报告，复用现有适用的协议及观测能力 |

现有实验客户端包含固定 24-DAG、模拟等待、定长输出和历史兼容逻辑。
新 benchmark 需要独立的真实任务运行入口，不把这些负载专用规则带入 BFCL 或 SWE。
接入以客户端为主；如果发现服务端协议缺口，先说明具体问题和所需变更，再扩展实现范围。

### 5.2 请求身份与工具事件

每次实际模型请求使用新的 `tc-` 加规范小写 UUID4 hex，顶层 `request_id` 与 `lifecycle_id` 相同。
任务、步骤与请求尝试的关联单独记录，不将响应 API 自带前缀的 ID 当作生命周期 ID。

工具执行遵循以下顺序：

```text
模型生成完成
  -> stall_started 得到确认
  -> 执行真实工具
  -> stall_finished 得到确认
  -> 提交后继模型请求
```

同一次模型响应包含多个工具动作时，协调该次完整等待阶段的事件，避免重复启动同一生命周期。
异常、取消和超时路径也要记录终态并清理任务，不能静默忽略事件失败。
`base` 不发送 TokenCake 元数据和事件；`agent` 只发送元数据；两个 offload 组同时发送元数据和事件。

### 5.3 元数据规则

| 字段或信息 | 首轮设置 |
| --- | --- |
| `agent_type` | BFCL 为 `bfcl`，SWE 为 `swe_coder`；不同任务不创建新类型 |
| `importance` | 全部使用协议默认值 `0.0` |
| 应用时间 | 实际到达时间、到达偏移和已经过去的时间 |
| 深度、剩余深度、完成进度与汇合字段 | 保持协议默认值，不把最大步数当作真实 DAG 深度 |
| `offload_eligible`、`reusable_prefix` | 仅在核验上下文构造支持前缀复用的路径开启 |
| 工具时长 | 首轮不提供人工时长估计，使用服务端已有的历史学习，无历史时沿用默认 1 秒 |

不能利用未来实际调用次数、最终任务长度、正确答案或本次工具的未来真实耗时填写元数据。
当前调度器会将深度换算为进度，因此只填写已走步数、却没有可靠总深度，也可能产生错误的完成度信号。

## 6. 适配验证与机制观测

### 6.1 正确性验证

- 验证适配保留原有提示构造、采样参数、动作顺序、状态更新和评分输入。
- 验证请求身份、重试身份、事件确认顺序及不同并发任务间的状态隔离。
- 覆盖工具异常、模型超时、上下文超限、任务停止和清理路径。
- 检查实际传到服务端的元数据，避免模型封装丢弃扩展参数。
- 用真实任务完成从生成、工具执行、结果保存到评分的整个流程。

### 6.2 优化机制验证

观测实际 token 前缀、工具耗时、等待队列压力、KV 保存决策、完成保存量、GPU/CPU 命中和恢复成本。
事件成功只代表协议确认，不代表一定保存或命中了 CPU KV。
需要存在有效等待需求、可复用前缀和足够工具窗口，才能期望工具窗口保存产生收益。

针对提高并发的要求，增加 cgroup 实际内存占用、内存限制、OOM 事件、内存/CPU pressure、GPU 占用和外部 GPU 进程观测。
当前容器内存上限为 240 GiB，CPU 配额等价于 36 个核心；压力分析以容器限制为依据。
同时观察 GPU KV 使用率、等待请求、准入暂缓和抢占，不能仅凭提高了并发就认定已经产生 KV 容量压力。

BFCL 本地函数可能很快，允许出现 offload 无收益或回退的结果，不增加人工等待来改变结论。
SWE 的长工具操作也不保证收益，仍需检查 GPU 缓存竞争、后继命中及传输净成本。
当前 H2D 由后继请求的真实前缀命中触发，没有预测式提前回载；CPU 副本也不增加 GPU 物理容量。

## 8. 计时、指标与验收

### 8.1 计时边界

应用 E2E 从任务计划到达计到提交结果或进入失败终态，包含客户端等待、服务排队、推理、真实工具执行和协议交互。
模型加载、一次性的环境与依赖准备，以及事后官方规则评分另行计时。
任务到达与实际开始时间分别记录，不能通过隐藏客户端队列改善表观延迟。
工具与传输累计时间可能重叠，不能直接从 E2E 中相减。

### 8.2 输出指标

| 类别 | 指标 |
| --- | --- |
| 主指标 | 相同时间预算内，官方评分通过的题数；15、30、60 分钟的正确任务完成曲线 |
| 任务质量 | BFCL 官方多轮准确率、SWE `%Resolved`，分别报告选定类别与任务集合 |
| 完成与失败 | 提交数、完成数、答错、空 patch、格式错误、上下文超限、超时、服务和环境错误 |
| 辅助性能 | 双方共同通过同一道题的配对 E2E，同时报告单方成功和失败；全任务 E2E 仅作诊断 |
| 系统指标 | 按输入、输出长度联合分组的 TTFT、TPOT 和吞吐；缺少逐请求时间戳时明确标为不可用 |
| 模型工作量 | 调用次数、实际输入输出 token、声明输出预算、重试次数 |
| 输出吞吐量 | 服务端共同前 30 分钟、服务端各自全程、客户端完整响应三个口径；同时报告相对变化与采样滞后 |
| 调度与 KV | 排队、准入暂缓、抢占、prefill、GPU/CPU KV 命中及可用的重算指标 |
| 工具与传输 | 真实工具时长、保存决策和完成保存量、D2H/H2D 开销 |

保留所有运行和失败，不只统计成功任务的延迟，也不把不可观测的指标记为零。
温度为零不保证所有后端生成完全相同的轨迹，工作量差异需结合质量结果解释。
正确完成曲线从组测量开始计时，成功时间取实际最终提交时间，再由离线评分确认。
失败消耗的时间保留在相同预算分母中；固定批次提前全部结束后曲线保持不变，不能外推持续到达吞吐。
没有共同成功题时，配对 E2E 为不可用；不能将单方成功除以零，或通过筛掉失败宣称加速。
实际 KV 复用率使用实际输入来源 token 计数，缓存查找命中率单独解释。
当前非流式日志可统计长度分组的 HTTP E2E，但没有逐请求首 token 和生成时间戳；不得将聚合 Prometheus 计时反向分配到长度分组。
新增逐请求服务端观测若用于后续对比，需要在两组统一接入并记录其开销，再运行相同配置。

输出吞吐量按用户追加的固定口径实现：

- 服务端使用 `vllm:generation_tokens_total`，每次采样仅合计当前模型的各 engine，不累加不同时刻的累计值，不计入输入 token。
- 共同前 30 分钟从并行测量计时账本的同一 `start` 事件起算，分母固定 1800 秒；各自全程以本组 `ended_at` 截止并使用本组 `wall_s`。
- 分子取截止前最后一个有效采样与 `metrics-start.prom` 的差；不使用关闭前 `metrics.prom`，也不包括组任务全部结束后等待另一组的空闲时间。
- 客户端分子使用 `model_work.reported_output_tokens`，除以本组 `wall_s`。它仅计完整响应，与可包含中断输出的服务端计数分开。
- 不除以并发数，不对逐请求速率简单平均，不用请求耗时总和代替墙钟；失败、超时、真实工具等待均保留。
- 记录末次采样的 timestamp、距窗口末尾的时间、采样间隔和异常；逐 engine 检查重置，不能用总计数增长掩盖单个 engine 的重置。
- 没有覆盖完整 30 分钟的功能批次明确标为该窗口不可用；采样缺失保留诊断，不能补造采样。
- 同时展示共同窗口与各自全程，不只选择有利区间；输出吞吐量与正确解题效率分别解释。

### 8.3 验收原则

适配验收要求请求与任务身份正确、事件及异常路径可追踪、评分输入完整、所有预定任务有记录。
模型答错不等于适配失败，服务或环境失败也不能伪装成正常完成。

质量以不下降为目标，沿用前轮提出的 1 个百分点非劣容忍界，结合任务配对的区间判断。
20 题只用于验证流程、观察问题和估计成本，不用于证明质量等价。
区间不足以支持结论时标记不确定，不把很小的观测差异直接解释为等价。

性能按各负载点如实报告收益与回退，旧模拟实验的 25% 提速作为参考，不作为本轮首轮测量的硬性通过条件。
不以改变任务集合、减少任务步骤、强制缩短输出、隐藏失败或延长工具等待来获得提速结论。
