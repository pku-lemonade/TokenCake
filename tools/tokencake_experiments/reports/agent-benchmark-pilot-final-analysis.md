# Agent Benchmark 试跑最终分析

更新日期：2026-09-08。四组试跑与评分已完成，实验已停止，正式全量已按用户要求取消。

本文先解释统计口径，再比较 `base` 与 `agent_offload`，说明前 30 分钟和全程结果为什么不同，最后结合正确率、机制指标及另外两组判断结论范围。
本次 SWE 试跑中，`agent_offload` 的三个输出吞吐口径相对 `base` 分别提高 **27.6%、8.6%、6.8%**；正确题数为 **1/20 对 0/20**。
输出吞吐有所改善，但当前小样本不能证明稳定的正确解题效率提升。

**1. 测试对象与基本单位。** 首先同时运行 GPU 0 `base` 与 GPU 1 `agent_offload`，两组各使用一张 A800 80GB。
随后再运行 `agent` 与 `offload`，因此四组不是在同一个时间段测量。

| 比较条件 | 本轮设置 |
| --- | --- |
| 模型 | Qwen2.5-14B-Instruct，BF16 |
| 服务 | 最大上下文 32,768，显存比例 0.5，批 token 预算 8192 |
| CPU KV | 启用 offload 的配置使用 100 GiB 容量 |
| SWE 任务 | 每组相同 20 题，使用 mini-swe-agent，每组最多 16 个任务同时在途 |
| 任务释放 | 闭环执行：工作位空出后释放下一题；20 题全部释放后不再补入新题 |
| 执行预算 | 单题最多 250 步、3600 秒；单次模型请求最多 600 秒、shell 命令最多 60 秒 |

一项 SWE **任务**是一道修复题；一次模型**请求**只是这道题执行中的一步。
一次请求完整返回后，agent 可能继续执行工具、再次请求模型，最终仍可能提交错误补丁或超时。
因此“任务结束”“收到完整响应”“任务正确解决”是三个不同事件。

四组的任务、初始提示、模型与生成配置一致，20/20 题的初始提示哈希和输入 token 已核对。
后续使用真实生成历史和真实工具结果，实际请求次数、上下文长度与任务结束时刻会不同；相同初始输入不能保证相同实际工作量。

**2. 三个吞吐口径由两个维度组成。** 第一个维度是**统计多长时间**，第二个维度是**从哪里统计输出 token**。
“共同前 30 分钟”“各自全程”描述时间范围；“服务端”“客户端完整响应”描述输出计数来源。

| 名称 | 时间从哪里开始、到哪里结束 | 哪些输出进入分子 | 回答的问题 |
| --- | --- | --- | --- |
| 共同前 30 分钟，服务端 | 两组共用起点与截止，均为第 0–30 分钟，分母固定 1800 秒 | 服务端在该窗口内记录的生成 token | 给两组相同的 30 分钟，分别能生成多少输出？ |
| 各自全程，服务端 | 每组从自身任务执行开始，到本组 20 题全部进入终态 | 本组截止前服务端记录的生成 token | 本组整个固定批次运行下来，平均每秒生成多少输出？ |
| 各自全程，客户端完整响应 | 与上一行相同，每组使用自身全程 | 客户端完整收到响应并记录 usage 的输出 token | 整批运行下来，平均每秒收到多少有完整记录的模型输出？ |

这里的**“共同”指两组使用相同时间边界**，两组的输出分别统计。
这里的**“各自全程”允许时长不同**：`base` 运行 **36.64 分钟**，`agent_offload` 运行 **60.02 分钟**。
“全部结束”包含成功、错误提交、上下文超限和超时等终态；`base` 较早结束不代表它更早解决了全部题目。

这里的**“客户端完整响应”指一次模型调用完整返回**，不是整道题完成或答案正确。
例如一次请求超时前服务端已生成 100 token，客户端没有拿到完整响应和 usage：这部分可能进入服务端分子，但不进入客户端分子；这次超时消耗的时间仍进入两种口径的分母。

三个口径均为“输出 token 总数 / 一次墙钟时间”。
墙钟包含排队、prefill、decode、工具执行、等待、失败与超时；不包含模型启动和本组全部结束后等待另一组的空闲时间。
每组只有一张 GPU，token/s 就是 token/s/GPU；不除以 16 并发数，不平均逐请求 token/s，不使用各请求耗时之和。

**3. base 与 agent_offload 的数值。** 以下除法中的时间单位均为秒，所得速率单位均为 token/s/GPU。

| 口径 | base：输出 / 时间 = 吞吐 | agent_offload：输出 / 时间 = 吞吐 | 相对变化 |
| --- | ---: | ---: | ---: |
| 共同前 30 分钟，服务端 | 83,292 / 1800 = **46.27** | 106,239 / 1800 = **59.02** | **+27.6%** |
| 各自全程，服务端 | 95,659 / 2198.273171 = **43.52** | 170,156 / 3600.932717 = **47.25** | **+8.6%** |
| 各自全程，客户端完整响应 | 95,692 / 2198.273171 = **43.53** | 167,360 / 3600.932717 = **46.48** | **+6.8%** |

相对变化统一为 `(agent_offload 吞吐 / base 吞吐 - 1) × 100%`，使用原始精度计算后再显示有限小数。
前两行改变了时间窗口；后两行中，每一组自己的分母保持不变，改变的是输出计数来源。
所以三个百分比不是同一指标的三个阶段。

**4. 为什么全程提高 8.6%，小于前 30 分钟的 27.6%。** “全程吞吐”是整个运行期间的平均值，不是最后一刻的瞬时速率。
平均值取决于各时间段的速率，以及每段占全程的时间比例。

将同一批服务端输出拆成前 30 分钟和之后的剩余部分，可得到：

| 全程平均的组成 | base | agent_offload |
| --- | ---: | ---: |
| 前 30 分钟平均输出速率 | 46.27 token/s | 59.02 token/s |
| 30 分钟后继续运行的时间 | 398.27 秒，约 **6.64 分钟** | 1800.93 秒，约 **30.02 分钟** |
| 这段新增的服务端输出 | 12,367 token | 63,917 token |
| 这段平均输出速率 | **31.05 token/s** | **35.49 token/s** |
| 这段占各自全程的比例 | **18.1%** | **50.0%** |

两组后段速率都低于各自前 30 分钟，但这段在 `agent_offload` 全程中的权重更大，因此对其全程平均的拉低更明显。
其全程平均从 59.02 降到 47.25，`base` 从 46.27 降到 43.52，两者比值对应的增幅便从 27.6% 变为 8.6%。
全程平均按时间加权；用各段输出 token 和时长直接计算：

```text
base          ：(83,292 + 12,367) / (1800 + 398.273171)  ≈ 43.52 token/s
agent_offload ：(106,239 + 63,917) / (1800 + 1800.932717) ≈ 47.25 token/s
```

表中权重和速率、上式中的时长仅显示有限小数，分析使用原始精度。
为与既定口径精确相加，分段表的剩余时间使用 `wall_s - 1800`；共同起点比各组自身起点早约 3.4 毫秒，实际 timestamp 差也单独保存在分析 JSON 中。
两组后段长度和生成轨迹不同，表中 31.05 与 35.49 不能直接作为相同工作量下的配对加速比。

![两组全程平均中各时间段的权重](/root/autodl-tmp/tokencake-agent-bench/results/pilot-first-pair-window-weights-20260908-01.png)

图中深色均为共同前 30 分钟，浅色斜线为各自剩余时间；条内是该时间段的平均输出速率，右侧是全程平均。
可导出 [SVG](/root/autodl-tmp/tokencake-agent-bench/results/pilot-first-pair-window-weights-20260908-01.svg)。

上述是平均值变化的计算原因。**后段为什么输出较慢，还需要看当时的任务和服务状态。** 原始日志提供了以下证据：

- 第 30 分钟时，`base` 剩 4 个未结束任务；`agent_offload` 剩 11 个。`base` 后续四题以 3 个上下文超限和 1 个格式错误结束，因此它的低吞吐后段较短。
- `agent_offload` 在前 30 分钟平均有约 **2.81** 个请求处于服务端运行状态，之后约为 **1.26** 个；之后仍平均有约 **7.70** 个请求排队。这是对连续采样按时间加权的观测，16 个应用工作位不等于 GPU 始终同时运行 16 条请求。
- 以完整响应收到时刻分组，`agent_offload` 前 30 分钟请求的输入长度中位数为 **10,183.5 token**，之后为 **21,192.5 token**。这说明后段所处理的完整响应通常来自更长的上下文；跨越分界的响应按收到时刻整条归组，不能将该分组当成窗口内生成 token 的统计。
- `agent_offload` 后段有 2 个任务触及独立 600 秒模型请求时限，最后还有 9 个任务在约第 60 分钟耗尽任务时限。这些任务在结束前占用的排队、生成和等待时间全部保留。

更长的上下文、较少的同时运行请求和持续排队，与后段较低吞吐同时出现；这与当前完整容量预留在较长请求下限制准入的机制相符。
但请求轨迹和输出长度也在变化，旧日志不足以精确分配长上下文、容量预留、工具执行及生成差异各自造成的影响。
可以确定的是：**27.6% 到 8.6% 比较的是两个不同时间窗口的平均值，不能单凭这个变化认定优化随时间减弱。**

作为截止时间影响的补充核对，在 `base` 结束的同一时刻截断两组，服务端累计输出为 95,659 与 124,117 token，同窗比值为 +29.7%。
之后 `agent_offload` 又运行约 23.38 分钟，新增 46,039 token，平均约 32.82 token/s，进一步拉低了它的全程平均。
这是根据已知结束时刻补做的诊断窗口，仅用于解释截止时间的影响，不替代原定的三个报告口径，也不是新增独立实验。

**5. 为什么客户端完整响应的提升又降到 6.8%。** 从 8.6% 到 6.8%，每组分母都不变，差别完全来自记录的输出分子。

| 各自全程的输出计数 | base | agent_offload |
| --- | ---: | ---: |
| 服务端截止前末次采样 | 95,659 | 170,156 |
| 客户端完整响应 usage 合计 | 95,692 | 167,360 |
| 服务端计数减客户端计数 | -33 | +2,796 |
| 模型请求尝试 / 完整响应 | 587 / 587 | 845 / 834 |

`agent_offload` 有 11 次未完整返回的请求，服务端计数可能包含其中已生成的部分输出。
同时，服务端依赖定期采样，末次采样不是精确截止时刻；`base` 客户端比服务端多 33 token 就体现了两种计数不能要求完全相等。
因此 2,796 是这两个计数的**净差值**，不能全部直接命名为“丢失 token”或精确归到某一次超时。
使用客户端分子后，组合组的速率变为 46.48，基线为 43.53，相对变化为 6.8%。

**6. 吞吐改善是否代表解题更有效。** 本轮仍需以正确任务数回答这个问题。

| SWE 正确任务数 | base | agent | offload | agent_offload |
| --- | ---: | ---: | ---: | ---: |
| 第 15 分钟 | 0 | 0 | 0 | 1 |
| 第 30 分钟 | 0 | 0 | 0 | 1 |
| 第 60 分钟 | 0 | 0 | 0 | 1 |
| 整批最终结果 | 0/20 | 0/20 | 0/20 | 1/20 |

唯一正确题为 `agent_offload` 的 `sympy__sympy-16766`，在组开始后 **306.45 秒**提交，离线评分确认通过；该题自身 E2E 为 **203.08 秒**，计时起点不同。
失败和空补丁不增加正确完成曲线，失败消耗的时间保留；固定批次结束后不假定继续有新题到达。
任意两组都没有共同成功题，因此共同成功任务的配对 E2E 不可用；也不能把 1 对 0 转成有限倍数的解题加速。
80 个 SWE 任务终态和评分完整。错误提交、空补丁、格式错误、上下文超限和超时均保留在 20 题分母中。

SWE 在独立 `custom_local` 环境中使用冻结官方测试脚本、解析器及 resolved 规则评分。
固定 20 题均已验证原始版本和参考修复；Django locale 修复后的保存预测复核未改变任何通过数。
这些检查不能证明本地原生依赖与官方 Docker 环境完全等价；20 题、每组一次的试跑也不能证明统计稳定性或质量非劣。
正确完成与累计输出的完整曲线见 [四组详细报告](agent-benchmark-four-mode-pilot.md)。

**7. 哪些机制指标有所改善，代价是什么。** 以下是整个运行窗口内的聚合诊断，未按相同长度或相同任务轨迹配对。

| 机制指标 | base | agent_offload | 本轮变化 |
| --- | ---: | ---: | --- |
| 实际复用输入 token 比例 | 9.97% | 10.39% | 增加约 0.42 个百分点 |
| 其中 CPU 回载输入比例 | 0% | 1.14% | 已观察到 CPU KV 复用 |
| 相邻生成 token 平均间隔 | 46.80 ms | 34.25 ms | 缩短 26.8% |
| 按请求平均 TPOT | 51.73 ms | 36.55 ms | 缩短 29.3% |
| 平均 TTFT | 21.20 s | 37.11 s | 首 token 等待更长 |
| 平均排队 | 18.06 s | 34.65 s | 增加 91.8% |
| 原生抢占计数 | 11 | 0 | 组合组未观察到抢占 |

这些指标支持“本轮组合组生成间隔更短、抢占更少，同时排队更久”的描述。
实际缓存复用率只小幅增加，不能把吞吐变化全部归因于大幅减少 prefill 重算。
传输累计时间可能与计算和工具时间重叠，不能直接从墙钟扣除；原生基线也没有可直接对应的重算计数，无法给出可信的重算降幅。

历史客户端采用非流式请求，缺少逐请求首 token 与 decode 时间戳。
已有日志可以按输入输出长度分组统计 HTTP E2E，但不能恢复对应的 TTFT/TPOT；HTTP E2E 除以输出 token 也不能替代 TPOT。
原生追踪的无模型夹具只验证采集路径，构造的时间不能补入这轮数据。

**8. 另外两组与 BFCL 提供的补充证据。** 所有配置都保留相同三个口径，避免只呈现有利结果。

| SWE 输出吞吐，token/s/GPU | base | agent | offload | agent_offload |
| --- | ---: | ---: | ---: | ---: |
| 共同前 30 分钟，服务端 | 46.27 | 54.64 | 41.92 | 59.02 |
| 各自全程，服务端 | 43.52 | 41.88 | 31.42 | 47.25 |
| 各自全程，客户端完整响应 | 43.53 | 41.89 | 31.33 | 46.48 |

`agent` 前 30 分钟相对 base 为 +18.1%，全程服务端和客户端均约 -3.8%，没有正确题。
`offload` 三个口径分别为 -9.4%、-27.8%、-28.0%，但实际缓存复用率达到 78.88%，说明高复用率不自动带来高整体吞吐。

`offload` 有六段连续采样满足“运行请求为 0、排队请求大于 0、生成计数不增长”，合计 **2277.002 秒，占自身墙钟 58.4%**。
这里是单独 `offload` 配置的停滞，不能将这段时间归到 `agent_offload` 上解释前文的 8.6%。
这些时间完整计入其分母；多次恢复发生在超时取消之后，没有人工重启。
无模型调度夹具复现了“回载后队头分配失败阻挡后续就绪请求”的可能机制，但缺少真实逐请求分配及通知记录，历史根因仍未确定；详见 [停滞诊断](agent-benchmark-offload-stall-diagnosis.md)。

两对共享 cgroup 内存采样峰值均约 **239.99 GiB / 240 GiB**，没有 OOM 或 OOM kill。
它包含两组进程和文件缓存，不能当作单组 RSS 或 CPU KV 实际占用，也不能据此认定内存节省。

BFCL 每组只有 Base 2 题、Long Context 2 题，四组均 0/4，官方失败涉及工具状态不符、执行结果缺失或某轮缺少模型动作。
每组最多 4 个任务并发，工具执行总计约 5.5–8.1 ms，CPU 回载输入 token 为 0；保存/回载字节和耗时计数缺失，保持不可用。
因此这轮 BFCL 验证了多轮执行、记录及官方评分接入，没有覆盖 16 并发或长工具等待下的 CPU KV 收益。
两种 agent 主要顺序调用模型，本轮也不能完整验证并行分支汇合与跨类型预留借用。

BFCL 首对的组合组输出 5,392 token，base 为 1,272 token，轨迹不同；108.87 秒与 24.95 秒不能直接解释为框架减速。
首对功能检查与环境准备重叠，速率仅作记录；四组均不足 30 分钟，该固定窗口不可用。
初次 BFCL 的状态序列化失败及耗时保留，修复后另建目录重跑，未混入有效试跑准确率分母。

**9. 采样边界与复核依据。** 服务端精确筛选 `vllm:generation_tokens_total`，只合计同一时刻当前模型的各 engine，再减 `metrics-start.prom` 初始值；四组初始值均为 0。
首对共同起点为 `1788832262.4999597`，第二对为 `1788840641.3909407`，共同窗口截止均为起点加 1800 秒。
全程按本组 `tasks/execution.json` 的 `ended_at` 截止，分母严格使用 `wall_s`。
窗口末端取 `metrics.jsonl` 中截止前最后有效样本，不使用关闭前的 `metrics.prom`；客户端分子取原始报告的 `model_work.reported_output_tokens`。

| 窗口末次采样距截止的时间，秒 | base | agent | offload | agent_offload |
| --- | ---: | ---: | ---: | ---: |
| 共同前 30 分钟 | 1.730 | 0.689 | 0.587 | 0.177 |
| 各自全程 | 1.703 | 1.329 | 1.324 | 1.957 |

逐 engine 检查未发现计数器重置、序列缺失或重复、损坏采样、时间戳逆序，也没有超过 4 秒的采样间隔。
末次样本均滞后不足 2 秒，服务端窗口结果是近似值；统计按末次有效样本处理，没有补造截止时刻计数。
